# Follow-up review of the v0.3 specifications

Public technical extract: internal operational notes are omitted; locations refer to the reviewed revisions.

Reviewed 19 Sep 2026 against the working-tree revision described in
[the engineering response](2026-09-19-adversarial-review-response.md): six modified specifications,
269 added lines and 95 removed lines. The original review and response are retained as review history.

**Verdict: substantial corrections, with six remaining contract issues below.** Accepting a finding is
not the same as closing it. The indexer tail, zero rotary span, MTP index producer, separate precision
oracles, cold-invocation protocol, graph lifecycle and reasoning modes are materially improved.

R1, R3 and R4 require clarification before the Phase 0 contract is approved. R2, R5 and R6 concern later
work: record their closure conditions now, and satisfy them before implementing or evaluating the
affected feature. They do not require implementing the full model during the kernel spike.

## Remaining issues

### R1. High: a different activation can still qualify as the MOE parity baseline

Location: TEST-PLAN MOE-P-002 (line 244 in the reviewed revision).

The revised row allows the baseline's clamped SwiGLU to be verified **or the difference disclosed**.
Disclosure does not make different mathematical operations an eligible correctness or speed baseline.
The local contract clamps gate and up values; an unclamped runner can produce different results, and
its timing omits part of the required operation. Naming G16 fixes the format comparison but not this
loophole.

**Required:** a gate-eligible baseline must pass the same MOE correctness cases, including clamp-edge
inputs, using the same values, routing, precision contract and timed operation boundary. Time any
adapter work needed to perform that operation. A runner with disclosed semantic differences can be
reported as context, but cannot satisfy M5. A missing compatible baseline follows P3.

### R2. High: median user throughput does not enforce the per-user floor

Location: TEST-PLAN WL-001 (lines 378-379); PRD M1.

WL-001 reports the median across users but never states which statistic gates M1. Rates
`[1, 1, 1, 30, 30, 30, 30, 30]` have median 30, despite three agents being far below the requirement.
The new manifest must not make this an acceptable result.

**Required:** compute a rate for each of the eight fixed, paired session traces and require each to meet
both the absolute floor and its paired relative target. Report all eight rates, plus aggregate
statistics. Specify decode timing and count committed emitted tokens once; rejected draft tokens
never increase the numerator. Store the actual workload fixture before SYS evaluation, rather than
treating the list of manifest fields as an existing reproducible workload.

### R3. Medium: the NVFP4 zero-tensor case still divides by zero

Location: TEST-PLAN section 2 (lines 63-69), REF-004.

For an entirely zero expert tensor, the new global formula yields `g = 0`. Giving its zero blocks
scale 1 does not fix normalization: `w / (s_b * g)` remains `0 / 0`. The pinned dynamic ModelOpt helper
also lacks an explicit safe global-scale branch; pinning it is not evidence that this edge case works.
See [the pinned scaling and quantization implementation][modelopt].

**Required:** define a canonical zero-tensor encoding, such as zero codes and unit block/global
scales, or explicitly reject that tensor. Keep finite zero weights usable if practical. State this
intentional deviation from the raw helper's degenerate behavior; do not demand byte identity with
undefined upstream output. Cover zero blocks inside a nonzero tensor separately from an all-zero
tensor, and define rejection of non-finite codec input. The ordinary finite, nonzero path still needs
the byte-for-byte ModelOpt check.

### R4. Medium: the gather explanation and traffic accounting overclaim what address arithmetic proves

Location: TEST-PLAN SMLA-P-005 (line 187); response P1 (line 39).

P1 says the small rows cannot physically reach 80 percent cold. That is not established for both
listed widths: a 32-byte-aligned 288-byte row uses nine sectors, with 100 percent useful sector
efficiency; at a 16-byte offset it uses ten, with 90 percent efficiency. The 68/96 calculation applies
to an isolated 68-byte row without sector reuse. Neither calculation measures throughput relative to
the streaming benchmark.

The row also calls sectors computed from addresses "transferred bytes". Addresses give a sector
footprint estimate. Cache reuse, repeated loads across heads, transaction requests and device-memory
traffic are different quantities. NVIDIA distinguishes [requested, actual global and DRAM
throughput][bandwidth]. The numerator `K * row_size` also needs its per-query versus whole-launch scope
and treatment of head reuse stated.

**Required:** label predicted footprints separately from measured traffic; define whole-launch useful
bytes, repeated-head accounting, output stores and profiler counters or their unavailability. Run
the matched CUDA gather before attributing a failed absolute target to the compiler. Keep the
80-percent target explicit: if both implementations miss it, record an access-pattern or hardware
limit investigation, not evidence that changing kernel language fixes it. Future-format measurements
are report-only because of Phase 0 scope, not a claimed impossibility for 288-byte rows.

### R5. Medium: the proposed full-model equivalence gate is still not executable

Location: PRD proposed M3 (line 82); TEST-PLAN golden tests (lines 341-354).

An official runtime's own "run-to-run and kernel-variant" noise floor does not identify a fixed
experiment. Repeating one deterministic configuration can give zero KL. Choosing different variants
later can change the tolerance. The proposal also requires identical checkpoint files without naming
a runtime/adapter that can load the chosen G32-E4M3 build. The [pinned FlashInfer preparation][prepare]
is not evidence of support for that format in a complete official model runner.

**Required before Phase 1 evaluation:** select the actual reference runner and format, verify its
loader and semantics, and freeze the noise-floor experiment, aggregation, zero-floor handling and
pass threshold before testing engine results. Distinguish this engine-equivalence gate from the
quantization-quality gate. A selected BF16 acquisition plan remains necessary for the latter if it is
retained; listing three acquisition options does not execute a reference run.

P4 changes the kind of quality evidence required. It should be described as a replacement/deferment
of a gate, not justified merely by saying that no numeric threshold was lowered.

### R6. Medium: D1's chunk and greedy guarantees still need one consistent execution scope

Location: DEV-GUIDELINES section 1.3 (lines 36-44); TEST-PLAN SAMPLE (line 330), API-006.

D1 is still titled batch- and chunk-invariant while its new exception requires the same algorithm
path. Choosing the same chunked algorithm does not by itself fix arithmetic grouping when chunk
boundaries change. SAMPLE promises greedy MTP equality under D1 without carrying that qualification
through to recurrent versus multi-token verification paths.

**Required before those kernels are implemented:** either define a canonical recurrence/reduction
schedule for all D1 paths, including prefill, verification and cache reuse, or narrow the guarantee
to explicitly fixed execution partitions. State the same scope in SAMPLE, API-006 and the guidelines.
Keep sampler correctness with identical supplied target distributions separate from model-forward
differences. The [vLLM losslessness explanation][speculation] makes this numerical distinction too.

## Technical decisions for the next revision

The technical lead accepts the following bounded decisions. These are design decisions, not evidence
that any hardware gate has passed or authorization to publish a release.

| Proposal | Decision |
|---|---|
| P1 | Accept the GLM-only Phase 0 scope, keeping the 80-percent target; implement R4's accounting and diagnosis before approval of the measurement contract. Future row widths are report-only. |
| P2 | Accept G16 as the Phase 0 MOE parity format. G32 retains correctness tests and measurements; it has no demonstrated parity or full-model reference support. Resolve R1. |
| P3 | Accept provisional-only status when a compatible baseline is missing. It cannot satisfy M5. |
| P4 | Do not approve the replacement as written. Complete R5's reference and tolerance protocol before the Phase 1 gate; existing quality obligations remain open. |
| P5 | Accept M7 as a v1.0 release criterion. |
| P6 | Accept compute-kernel time as the Rust-share denominator. Sum kernel durations across both GPUs, counting all compute library kernels by implementation origin. Report NCCL, copies and elapsed decode-step time separately. A Rust launcher does not make a foreign kernel Rust. |
| P7 | Accept the proposed smoke-suite membership as a design starting point. Freeze fixtures, task versions and justified thresholds before its first qualification run; no M8 pass until then. |

Use explicit statuses in the response: corrected in the specification; awaiting a defined future
contract; awaiting reference evidence; hardware validation pending. The current review does not
require detailed Phase 1 implementation during Phase 0.
